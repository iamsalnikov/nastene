# Ручной план тестирования новостной ленты

**Маршрут:** `GET /news` (auth required, пагинация `?offset=N`, по 20 записей).
**Среда:** `task up && task migrate-up && task run`. Лента строится асинхронно через RabbitMQ → после каждого действия подождать ~1-2 сек перед проверкой `/news`.
**Аккаунты:** заведи минимум **A, B, C** через инвайты. A↔B — друзья, C — посторонний.

---

## 1. Базовый fanout постов

| # | Действие | Где смотреть | Ожидаемое |
|---|---|---|---|
| 1.1 | A постит на свою стену | B → `/news` | Запись появилась |
| 1.2 | То же | C → `/news` | Записи нет |
| 1.3 | A постит на стену B | A → `/news` | Записи нет (только владельцу) |
| 1.4 | То же | B → `/news` | Запись появилась |
| 1.5 | A постит на стену B | C → `/news` | Записи нет |
| 1.6 | A создаёт **граффити** на своей стене (через `/graffiti/{id}`, рисует, сохраняет) | B → `/news` | Запись с превью граффити, без `body_text` |

## 2. Fanout комментариев

Setup: A постит на своей стене, под постом комментируют B, потом C (если C добавили в друзья A). Если C не друг — пусть прокомментирует D.

| # | Действие | Где смотреть | Ожидаемое |
|---|---|---|---|
| 2.1 | B комментит пост A | A → `/news` | Запись о комменте B |
| 2.2 | То же | B → `/news` | Записи о **своём** комменте нет (автора не уведомляем) |
| 2.3 | D комментит тот же пост | B → `/news` | Запись (B — предыдущий комментатор) |
| 2.4 | D комментит ещё раз | B → `/news` | Каждый новый коммент = новая запись. Дубликаты исключены только при повторе одного и того же `comment_id` (идемпотентность события) |

## 3. Privacy: скрытие/возврат

Setup: у A есть пост на своей стене, B видит его в `/news`.

| # | Действие | Где смотреть | Ожидаемое |
|---|---|---|---|
| 3.1 | A: `/settings/privacy/wall` → view = **nobody** | B → `/news` | Записи A пропали |
| 3.2 | То же | A → `/id{A}` | A видит свою стену (себе всегда видно) |
| 3.3 | A возвращает view = **friends** | B → `/news` | Записи A снова появились (теми же позициями по времени) |
| 3.4 | A: view = **public**; C (не друг) заходит в ленту | C → `/news` | Старых постов A нет (бэкфил не делается) |
| 3.5 | A постит **новый** пост при view=public | C → `/news` | **Не появляется**: C не друг → fanout его не включает (public влияет на просмотр стены, не на ленту) |

> Это важный инвариант: лента собирается по дружбе на момент **создания поста**, privacy лишь прячет/раскрывает уже существующие записи.

## 4. Бан

Setup: A и B друзья, в ленте B есть посты A и наоборот. У A есть pending friend_request от/к кому-то.

| # | Действие | Где проверить | Ожидаемое |
|---|---|---|---|
| 4.1 | A: `/id{B}/ban` | A → `/news` | Записи B исчезли |
| 4.2 | То же | B → `/news` | Записи A исчезли |
| 4.3 | То же | A → `/friends`, B → `/friends` | Дружбы нет, pending requests между ними тоже нет |
| 4.4 | То же | A → `/id{B}` и B → `/id{A}` | Профили взаимно невидимы (видно только имя) |
| 4.5 | После бана A постит | B → `/news` | Не приходит |
| 4.6 | После бана B комментит чей-то общий пост (если такой есть) | A → `/news` | Уведомление о комменте B не приходит |

## 5. Unban (асимметричный)

Setup: продолжение пункта 4.

| # | Действие | Где проверить | Ожидаемое |
|---|---|---|---|
| 5.1 | A: `/id{B}/unban` | A, B → `/news` | Старые записи **не восстанавливаются** |
| 5.2 | То же | A↔B → `/friends` | Дружбы по-прежнему нет (нужно повторно отправить request) |
| 5.3 | A постит | B → `/news` | Не приходит (друзьями ещё не стали) |
| 5.4 | B шлёт friend_request → A принимает → A постит | B → `/news` | Новый пост появляется. Старые посты A до бана — нет (не бэкфилим) |

## 6. Удаление поста/коммента (cascade)

| # | Действие | Где смотреть | Ожидаемое |
|---|---|---|---|
| 6.1 | A удаляет свой пост (`POST /post/{id}/delete`) | B → `/news` | Запись о посте и все записи о его комментах исчезли (FK CASCADE) |
| 6.2 | B удаляет свой коммент (`POST /comment/{id}/delete`) | A → `/news` | Запись об этом комменте исчезла, остальные записи поста на месте |

## 7. Пагинация и порядок

| # | Действие | Ожидаемое |
|---|---|---|
| 7.1 | Создать 25+ событий для одного зрителя | `/news` показывает 20, есть ссылка/кнопка «дальше» (`?offset=20`) |
| 7.2 | Отсортированность | Свежие сверху, при равном `created_at` — больший `id` сверху |

## 8. Идемпотентность и асинхронность

| # | Действие | Ожидаемое |
|---|---|---|
| 8.1 | Перезапустить `feed-builder` сразу после поста A (до того как RabbitMQ доставил событие) | После старта worker дочитывает событие, запись появляется один раз |
| 8.2 | Если есть способ переслать одно и то же событие дважды (через RabbitMQ UI или заглушку) | Дубликата записи в ленте нет (UNIQUE partial индексы + `ON CONFLICT DO NOTHING`) |

## 9. Регрессии после P0/P1 фиксов

| # | Действие | Ожидаемое |
|---|---|---|
| 9.1 | Полный сценарий бана из пункта 4 при наличии нескольких комментов | Удаление feed-записей корректное (проверить SQL-логи `feed-builder` или вручную SELECT из `news_feed`) |
| 9.2 | Смена приватности на стене с большим количеством постов и зрителей | `wall.privacy.changed` обрабатывается за секунды, в `/news` у зрителей всё консистентно скрыто/восстановлено |

## Что проверять в БД (опционально, при сомнениях)

```sql
-- что сейчас в ленте у пользователя X
SELECT id, kind, post_id, comment_id, created_at, hidden_at
FROM news_feed WHERE user_id = X ORDER BY created_at DESC, id DESC;

-- сколько строк в ленте суммарно
SELECT COUNT(*) FROM news_feed;

-- увидеть какие индексы реально используются (после задействия)
SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE relname = 'news_feed';
```
